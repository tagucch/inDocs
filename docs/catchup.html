Catch-up briefing

inDocs キャッチアップ

AI エージェントに作らせた HTML を 1 か所に集めて、PC とスマホから読むための自分専用サイト。この 1 枚で、目的・構成・データの流れ・運用までを一通り把握できるようにまとめた。

更新 2026-10-28（水） 本番 indocs.tagucch.workers.dev GitHub tagucch/inDocs
何をするもの

Claude Code などが作った HTML を登録して、案件ごとの一覧から PC・スマホで読む。既読・スター・ピンは端末間で同期する。

どこで動く

Cloudflare Worker 1 つ（Hono）。管理画面は Preact の PWA、本体は R2、台帳は D1。

誰が入れる

Google ログイン後、secret の許可メールに載っているアカウントだけ。登録の仕組みはない。

どう登録する

PC の CLI indocs add file.html。Claude Code のスキルから「共有して」で動く。

01目的と参考元

AI エージェントに長い報告や調査結果を HTML で書かせると、チャットの中では読みづらく、ファイルは散らばる。inDocs はそれを 1 か所にため、PC でもスマホでも同じ一覧から開けるようにする。

発想は御田 稔氏（minorun365）の「HTML共有くん」から借りた。成果物を 1 か所にためる、既読を端末間で同期する、スマホから依頼を置く、という考え方は同じで、実装は AWS ではなく Cloudflare だけで完結するように組み替えている。コードは参考にしたが流用はしていない。

参考元
minorun365/html-share（Apache-2.0。S3 + CloudFront + Cognito + DynamoDB 構成）
要件
Cloudflare だけで動く／PWA として PC・スマホのホーム画面に置ける／指定した Google アカウントだけがログインできる
初期スコープ
一覧・既読同期・スター/ピン・検索・CLI/スキル・PWA に加え、インボックスとスマホ向け表のカード化。共有 URL と進行中フィルターは見送り

02全体構成

Worker は 1 つだけ。パスで役割を分け、配信 HTML は CSP の sandbox で隔離する。元の構成は閲覧面と管理面を別ドメインに分けていたが、workers.dev 1 つで始めるため、オリジン分離の代わりに opaque origin 化で同じ効果を得ている。

Hono 4Preact 10 + Vite 8@cloudflare/vite-pluginwrangler 4D1R2jose（ID トークン検証）TypeScript 7pnpm workspace

静的アセットは SPA フォールバック付きで配信し、/api/* /auth/* /view/* だけが Worker を先に通る（run_worker_first）。管理画面の CSP は public/_headers で、配信 HTML の CSP は Worker が付ける。

03画面と概念

用語意味どこで決まるか
ページ登録した HTML 1 枚。slug（英小文字・数字・ハイフン）が URL と一意性の鍵CLI がファイル名から slugify。--slug で固定可
プロジェクト一覧でカードにまとめる単位。表示名そのもの--project。省略時は Git リポジトリ名、なければ親フォルダ名
未読pages.updated_at が、自分が最後に読んだ版より新しい読んだ版は page_states.read_version。未設定なら初回ログイン時刻を基準にする
スター / ピンスターはプロジェクト単位とページ単位。ピンはプロジェクト単位で、ヘッダーの絞り込みチップになるユーザーごとに D1 に保存。端末間で同期
非表示一覧から隠すだけ。本体も URL も残り、「非表示 N 件」から戻せるpage_states.hidden
端末ペアリング済みの PC。CLI はここから発行された端末トークンで API を呼ぶ設定画面のコード（10 分・一度きり）→ indocs pair
依頼（request）スマホから置く「やっておいて」。PC の /inbox が引き取るインボックス画面。90 日で失効
確認カード（review）PC の作業から「承認してよいか」をスマホに投げる。承認かコメントが返る/mobile スキル → indocs review push。30 日で失効

管理画面の 4 画面

  • 一覧（/）: 上に「すべて／未読／スター／ピン留めプロジェクト」のチップ。本文は先頭に「スター」段、続いて「今日・昨日・今週・先週・今月・先月・N 月」の区切り（JST）。各区切りの中はプロジェクトのカードで、4 件を超える分は「他 N 件」に畳む。/ で検索
  • 閲覧（/p/:slug）: ヘッダー付きの全画面 iframe。開いた時点で既読になる。スター、新しいタブで開く、未読に戻す、一覧から隠す、読み直す
  • インボックス（/inbox）: 「Claude への依頼」フォームと一覧、「Claude からの確認」カード（承認ボタンとコメント欄）。60 秒ごと、画面に戻ったときにも再取得
  • 設定（/settings）: ログイン中のメールとログアウト、PC の登録（コード発行とコマンド表示）、登録済み PC の解除、ホーム画面追加の案内
表のカード化: 配信時に Worker が </body> の直前にスクリプトを差し込む。幅 640px 以下で、はみ出していて rowspan/colspan のない表だけを、行ごとのカード（1 列目を見出し、以降を「ラベル：値」）に畳む。

044 つの流れ

ログイン

  1. /auth/login が PKCE の verifier・state・nonce を 10 分の署名付き Cookie に入れ、Google へ送る
  2. /auth/callback でコードをトークンに交換し、ID トークンを Google の JWKS で検証（iss / aud / exp / nonce）
  3. email_verified かつ ALLOWED_EMAILS に含まれるときだけ、users を更新して 30 日の署名付き Cookie を発行
  4. 外れていれば 403。D1 には何も残らない

ページの登録と配信

  1. CLI が HTML を読み、同じフォルダ配下の画像・CSS・JS を data: URL に埋め込む（1 ファイル 10MB、HTML 15MB まで）
  2. PUT /api/device/pages/:slug に JSON で送る。Worker は R2 に pages/<slug>.html として置き、D1 を upsert
  3. 中身のハッシュが同じなら updated_at を進めない（未読にならない）
  4. GET /view/:slug はセッションを確認し、R2 から流しつつ表カード化スクリプトを注入。CSP sandbox 付き

インボックス（スマホ → PC）

  1. スマホで本文とプロジェクト名（任意）を入れて「頼む」。tasks に kind=request / status=waiting で入る
  2. PC で /inbox。indocs inbox が waiting の依頼を返す
  3. 引き取ったら作業前に indocs complete。取り込み済みの状態は持たず、開いたままなら「誰も拾っていない」を意味する
  4. 進捗と結果はチャットで返す

確認カード（PC → スマホ）

  1. /mobile が状況ページを indocs add で登録し、カード（題名・質問・文脈・推奨）を indocs review push --session で送る
  2. indocs review watch が 20 秒ごとに回答を待つ（既定 240 分）
  3. スマホで「承認」か「コメントを送る」。status が answered になる
  4. PC が pull で取り込み、対応後に complete。カードはインボックスから消える

05データモデル（D1）

テーブル主な列覚えておくこと
usersemail, first_seen_at, last_seen_at初回ログインより前に登録されたページは既読扱いにするための基準
pagesslug, title, project, project_label, source, device_id, content_hash, size, created_at, updated_at, deleted_at削除は deleted_at を立てるソフト削除。R2 の本体は消す
page_statesuser_email, slug, read_version, starred, hidden既読に戻すときは read_version = updated_at、未読に戻すときは空文字
project_statesuser_email, project, starred, pinnedプロジェクト単位のスターとピン
devicesid, token_hash, name, user_email, created_at, last_used_at, revoked_atトークンは SHA-256 のみ保存。解除は revoked_at
pairingscode_hash, user_email, created_at, expires_at, claimed_atコードは 32 文字のアルファベット（I/O/0/1 を除く）8 桁。UPDATE ... WHERE claimed_at IS NULL で一度きりを保証
tasksid, kind, user_email, device_id, session_id, title, body, target, context, recommendation, status, approved, response_text, 各時刻, expires_atkind は request / review、status は waiting / answered / completed。期限切れは一覧取得時に掃除

時刻はすべて ISO 8601 の文字列で持ち、文字列比較で前後を決める。複数の許可メールがいる場合、ページは共有、既読・スター・ピン・依頼・端末はメールごとに分かれる。

06API

ブラウザ用（owner）はセッション Cookie、CLI 用（device）は Authorization: Bearer の端末トークン。どちらも毎リクエストで許可メールを照合する。

系統メソッドとパス役割
authGET /auth/login?return=Google へ。戻り先は同一オリジンのパスだけ受け付ける
GET /auth/callbackコード交換・検証・Cookie 発行
POST /auth/logoutCookie を消す
GET /auth/meログイン中のメール。未ログインは 401
GET /auth/dev-loginローカル開発専用。DEV_LOGIN_EMAIL があり localhost のときだけ
ownerGET /api/owner/pagesページ一覧＋自分の既読・スター・非表示＋プロジェクト状態
PUT /api/owner/pages/:slug/stateread / starred / hidden の部分更新
PUT /api/owner/projects/:project/statestarred / pinned
POST /api/owner/pairingsペアリングコード発行
GET/DELETE /api/owner/devices[/:id]登録済み PC の一覧と解除
GET /api/owner/tasks?all=1未完了の依頼とカード（all で完了も）
POST /api/owner/tasks依頼を置く
POST /api/owner/tasks/:id/answer, DELETE /api/owner/tasks/:idカードに回答／依頼やカードを取り消す
devicePOST /api/device/pairコードを端末トークンに交換（認証なし）

GET /api/device/pagesページ一覧

viewGET /view/:slug配信 HTML。未ログインはログインへリダイレクト

07CLI とスキル

indocs は依存ライブラリのない単一ファイル（esbuild でバンドル）。この PC では ~/.local/bin/indocs がリポジトリの packages/cli/dist/indocs.mjs を指している。設定は ~/.config/indocs/config.json（0600）。

コマンドやること
indocs pair <code> --url <URL> [--name]この PC を登録する。名前の既定はホスト名
indocs add <file.html> [--project] [--title] [--slug] [--label]埋め込み → 登録。URL と埋め込めなかった参照を表示
indocs list [--json] / indocs remove <slug>一覧／削除
indocs whoami接続先と端末名の確認
indocs inbox [--json] / indocs complete <id...>依頼の取得／完了
indocs review push --session <id> [--file]カードを送る（標準入力の JSON でも可、1〜5 枚）
indocs review pull|watch --session <id> [--timeout-minutes]回答の取得／回答待ち（時間切れは終了コード 2）

環境変数は INDOCS_URL（接続先の上書き）と INDOCS_CONFIG_DIR（設定の置き場所）。終了コードは 401 のとき 3、それ以外のエラーは 1。

Claude Code のスキル

~/.claude/skills/ にリポジトリの skills/ を名前ごとにシンボリックリンクしている。いずれも CLI を使い、API を直接呼ばず、端末トークンを表示しない。

  • indocs-share: 「inDocs に共有して」「この HTML を追加して」で indocs add。未登録なら設定画面でのコード発行を案内する
  • inbox: /inbox。依頼を読み、作業前に完了にし、target と依頼文から作業フォルダを見極めて始める
  • mobile: /mobile。状況ページを登録し、カードを送り、回答を待って続ける。未回答のまま完了を宣言しない

08セキュリティ設計

  • 入口は許可リストだけ: サインアップはない。ALLOWED_EMAILS（secret）に無いメールはコールバック時点で 403 になり、D1 にも残らない。セッションや端末トークンも毎リクエストで再照合するので、外せば即座に締め出せる
  • 配信面の隔離: /view/* の CSP は sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox allow-top-navigation-by-user-activation。ドキュメントは opaque origin になり、Cookie・localStorage・同一オリジンの API に触れない。connect-src 'none'、form-action 'none'、frame-ancestors 'self'。CDN のスクリプトや Google Fonts は許す（隔離済みで、HTML の中身以上は漏れない）
  • 管理面の CSP: default-src 'self'、frame-ancestors 'none'。iframe 側には sandbox 属性を付けない（一部の組み込みブラウザが遮断するため。隔離はレスポンス側の CSP で担保）
  • CSRF: owner API の GET 以外は Origin が自分と一致しなければ 403。Cookie は HttpOnly / Secure / SameSite=Lax
  • 戻り先の検証: return は制御文字・バックスラッシュ・// 始まりを捨て、URL として正規化した後にも同じ条件を掛ける（/.//evil 対策）
  • 端末トークン: 生の値は端末にだけ返し、D1 には SHA-256。ペアリングコードは 10 分・一度きり
  • 開発用ログイン: DEV_LOGIN_EMAIL があり、かつ localhost からのときだけ。本番では 404

11決めたこと

論点選んだ方理由と捨てた案
認証Workers 上で Google OIDC を自前実装コードと secret だけで環境を再現できる。Cloudflare Access は Zero Trust 側の設定に依存するので見送り
オリジンWorker 1 つ、配信面は CSP sandbox で隔離workers.dev 1 つで始めたかった。別ドメイン 2 つに分ける案は、カスタムドメインを用意したときに /view/* を切り出せる形で残す
台帳サーバー（D1）が正。CLI は push するだけ元実装のローカル YAML を正とする方式は、複数 PC から登録すると衝突する
閲覧PC もスマホも iframeスマホでトップレベル遷移にすると、ホーム画面から開いた PWA で戻れなくなる
配信面の外部読み込みCDN スクリプトと Web フォントを許可Claude が作る HTML は Chart.js や Google Fonts をよく使う。sandbox で隔離済みなので管理面には届かない
フロントPreact 10 + Vite、フレームワーク最小一覧・既読・インボックスと状態が多く素の JS では辛い。Preact 11 は出たばかりで周辺の対応が読めず 10 系に
既読の基準初回ログイン時刻より前のページは既読新しい許可メールを足したときに全ページが未読になるのを避ける
スコープ外共有 URL、進行中フィルター、プルリフレッシュ一人で使う初版には不要と判断。設計は後から足せる
